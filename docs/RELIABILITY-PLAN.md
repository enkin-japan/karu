## 1. 核实结论

核实方式：按报告附录重新编译生产源码并在临时目录运行探针；逐条阅读报告引用的源码；
对报告未能测到的部分补充实测。全部探针只读写临时目录，没有启动或改动已安装的 Karu，
没有碰用户文档和偏好。环境：macOS 27.2，arm64，`swiftc -O`。

| 编号 | 报告判断 | 核实方式 | 结论与补充 |
|---|---|---|---|
| R01 | 保存不检测外部修改 | 探针复现 + 读码 | 成立。全仓库没有任何外部变化检测，手动保存与失焦自动保存都直接覆盖 |

|---|---|---|
| N01 | 经符号链接打开的文件，保存后链接被替换成普通文件，原目标文件不变；自定义扩展属性丢失，硬链接断开 | 对 `Data.write(options: .atomic)`（即 `DocumentController.write` 的写法）实测：`link.txt -> target.txt` 写入后变成普通文件，`target.txt` 内容未变；`com.example.tag` 属性消失；权限位保留。打开路径不解析符号链接。用符号链接管理配置文件的用户会直接遇到 |

## 2. 修复方案

共 15 个任务，分四个阶段。每个任务单独提交；每个阶段结束跑 `scripts/test.sh` 和
`scripts/visual-smoke.sh`，阶段一、二结束后装本机供实测。不升版本、不发布、不推送，直到用户说发布。

分工按 CLAUDE.md：跨文件实现交 implementer，小而可验证的交 chore-worker，
发布脚本和架构取舍由主会话处理，所有改动由主会话审过 diff 再提交。

### 阶段一：保住内容

#### F1 保存前检测外部修改，保存时保留文件身份（R01、N01）

- **记录磁盘状态。**`DocumentController` 在载入、重新载入、保存成功后记下 `DiskState`：
  设备号与 inode、大小、修改时间、文件字节的 SHA-256。
- **保存前核对。**先 `stat`：四项都没变就直接写。有变化再读文件算摘要，摘要相同（只是被 touch）
  也直接写，并刷新记录；摘要不同则抛出 `DocumentError.changedOnDisk`，不写入。
  文件已不存在时按现状重新创建，不算冲突。
- **写入方式。**先解析符号链接，写到真实文件；在同目录写临时文件，替换前再核对一次 `stat`，
  用 `FileManager.replaceItemAt` 完成替换，以保留原文件的扩展属性和访问控制；
  整个过程包在 `NSFileCoordinator` 里，以配合 iCloud 等协调写入方。
  对不参与协调的写入方，核对与替换之间仍有毫秒级窗口，这一点如实写进文档，不宣称消除。
- **界面。**手动保存遇到冲突，弹出选择（D1）。失焦自动保存遇到冲突不覆盖，
  复用现有的保存失败横条说明原因。任何失败都不清除未保存标记，也不删除草稿。
- **切回窗口时的检查（D2）。**窗口成为主窗口时做一次 `stat`，不常驻监听。
  磁盘有变化且缓冲区与基线一致，就重新载入并在状态栏提示；有未保存修改则只提示。
- **拆分。**保存、冲突判断和草稿检查点从 `EditorWindowController` 移入新的
  `DocumentPersistence`（仍在 KaruCore 内），窗口控制器只负责界面（对应 R14）。
- **涉及文件：**`App/DocumentController.swift`、`Editor/EditorWindowController.swift`、
  新增 `App/DocumentPersistence.swift`、`L10n/`、对应测试。
- **验收：**新增测试覆盖外部编辑、仅修改时间变化、删除后重建、被同步软件整体替换、
  经符号链接保存、带扩展属性的文件保存；冲突时磁盘内容、未保存标记和草稿都不变；
  自动保存遇冲突不写入。报告附录的 R01 探针输出变为 `external-change` 且抛出冲突错误。
  实机验证冲突弹窗、横条和自动重新载入。
- **分工：**implementer；`replaceItemAt` 是否保留属性先由主会话写探针确认，保留不了就改用
  `exchangedata` 类方案或逐项复制属性。

#### F2 草稿本区分"没有内容"与"读不出来"（R02）

- `ScratchpadStore.load()` 返回三种结果：不存在、读到文本、读取失败（带错误）。
- 解码失败时，把原文件改名为 `content.unreadable-<时间>.txt` 留在原目录，再打开空的草稿本，
  并在面板里提示旧内容的保存位置。读文件本身失败（权限、I/O）时不打开面板，只报错，
  这种状态下任何路径都不写回。
- **涉及文件：**`Scratchpad/ScratchpadStore.swift`、`Scratchpad/ScratchpadController.swift`、测试。
- **验收：**对不可解码内容、读取失败、改名失败三种情形注入故障，隐藏和退出后原字节都还在。
  报告附录的 R02 探针不再把文件写成 0 字节。
- **分工：**implementer。

#### F3 草稿检查点设最大间隔，失败可见（R05）

- 保留 1.5 秒去抖，另加最大间隔（初值 10 秒）：从第一次未落盘的编辑起计时，
  到点即写，不被后续输入推迟。普通文档和草稿本都加。
- `DraftStore.write` 返回成功或失败。失败时在状态栏提示一次，直到下次成功再重置；不弹窗。
- 后台写入改为只保留最新一份待写快照，慢盘上不积压；基线摘要比较移到后台队列。
- 草稿本输入期间改为后台落盘，隐藏和退出时同步落盘（两者都需要拿到写入结果）。
- **涉及文件：**`App/DraftStore.swift`、`App/DocumentPersistence.swift`（F1 新增）、
  `Scratchpad/ScratchpadController.swift`、测试。
- **验收：**用可注入的时钟证明持续输入 30 秒内至少按最大间隔落盘；写失败时状态可查询且不报告成功；
  慢速存储替身下待写快照不超过一份。
- **分工：**implementer，在 F1 之后做（同一个新文件）。

#### F4 草稿改为单文件提交（R06）

- 每份草稿一个文件 `<uuid>.draft`，一次原子写入。首行是 JSON 头，其后是原文：
  头里有格式版本、原路径、保存时间，以及草稿所基于的磁盘状态（F1 的 `DiskState`）。
- 读取方继续接受旧的"正文加 `.json`"成对文件；同一草稿首次按新格式写入后删除旧的一对。
- **涉及文件：**`App/DraftStore.swift`、测试。
- **验收：**在每个持久化步骤注入中断，恢复结果只能是完整旧版或完整新版；旧格式草稿仍能恢复。
- **分工：**implementer，可与 F3 合并为一次委派。

#### F5 恢复冲突时不删草稿（R07，D4 已定）

- 把判断抽成纯函数 `DraftRecovery.decide(draft:disk:)`，`AppDelegate.restoreDrafts` 只执行结果：
  - 磁盘内容与草稿所基于的版本一致：草稿套用到文件窗口（现有行为）。
  - 磁盘内容与草稿内容相同：草稿已无用，删除。
  - 其余情况视为冲突：照常打开磁盘版本，草稿另开未命名窗口作为恢复副本，状态栏说明。
  - 旧格式草稿没有基线信息，沿用修改时间判断，但冲突时同样另开副本而不删除。
- 启动时不弹窗的约定不变。
- **涉及文件：**`App/AppDelegate.swift`、新增 `App/DraftRecovery.swift`、`L10n/`、测试。
- **验收：**双方各自新增不同段落、仅修改时间变化、文件被替换、文件被删除四种情形都有测试，
  没有任何一种会丢掉唯一的一份内容。
- **分工：**implementer，依赖 F4。

### 阶段二：让输入成本可控

#### F6 搜索加时间预算和结果上限（R03）

- `SearchEngine` 改用 `enumerateMatches` 加 `.reportProgress`，接受时间上限和匹配数上限，
  返回结果以及是否被截断、因何截断。初值：单次 200 ms，匹配 50000 个。
- 查找栏在截断时显示"结果不完整"和原因；计数显示为"50000+"。
- 全部替换使用同一套预算，超时即放弃且不改动文档，绝不做部分替换。
- 匹配高亮只装饰可见区域内的匹配，滚动时补画（查找栏已有按范围补画的入口）。
- 第二步，仅当实测显示正常搜索会在 10 MB 以内的文档上撞到时间上限时才做：
  把匹配移到后台队列，按文档版本丢弃过期结果。
- **涉及文件：**`Search/SearchEngine.swift`、`Search/FindBarController.swift`、`L10n/`、测试。
- **验收：**`^(a+)+$` 对 40 个 `a` 加 `!` 在 0.3 秒内返回并标记超时；2 MB 文档里单字符 200 万次命中
  被上限截断且界面有提示；全部替换超时后文档与撤销栈都不变；现有搜索测试全部通过。
- **分工：**implementer。

#### F7 重写两个格式化器的底层表示（R04、R10、N02、N03）

- **表示。**不再把全文转成 `[Character]`。在 UTF-8 字节上用游标扫描，直接写入预留容量的输出缓冲。
- **JSON。**单遍流式重排，用显式栈记录容器类型，不建 token 数组，不递归。
  另提供只校验不输出的入口，语言识别改用它（N03）。
- **XML。**节点只保存对源缓冲的字节范围；解析与渲染改为显式栈。同时修掉三处边界（D5）：
  元素内的处理指令、带内部子集的 DOCTYPE、未加引号或重复的属性。
- **上限（D6）。**嵌套超过上限或输出超过上限时返回错误，由现有的格式化错误提示显示，文档不变。
- **线程。**512 KB 以上的输入在后台队列计算，完成后核对文档版本，未变才作为一次可撤销编辑写入；
  期间文档被改动则放弃并提示。小输入保持同步。
- **预算口径。**用 `/usr/bin/time -l` 的 peak memory footprint 减去"仅载入文件"的读数，
  作为格式化的瞬时增量，记入 `docs/DEVELOPMENT.md`。目标是典型输入不超过文件大小的 4 倍；
  实测达不到时，把实际数字和原因报给用户，由用户决定是否改 ARCHITECTURE.md 的预算。
- **涉及文件：**`Format/JSONFormatter.swift`、`Format/XMLFormatter.swift`、`Format/FormatDispatch.swift`、
  `Highlight/LanguageSniffer.swift`、`Editor/EditorWindowController.swift`（格式化动作）、测试与夹具。
- **验收：**现有格式化测试逐字节不变；新增深嵌套（上限处通过、超限报错、不崩溃）、
  含长字符串、密集 token、多字节字符的用例；XML 三处边界的正反例；
  5.55 MB JSON 与 4.95 MB XML 的峰值增量各记录一次并与本文第 1 节的 235 MB、132 MB 对比。
- **分工：**JSON 与 XML 分给两个 implementer 并行（文件不重叠）；线程与界面接线随后由其中一个完成。
  这是本方案里最大的一项。

#### F8 导入缓存的最新条目也守上限（R08）

- 淘汰完其他条目仍超限时，把最新条目降为仅名字；仍超限则不缓存，并计入一个可观测的拒绝计数。
- **涉及文件：**`Imports/ImportSummaryCache.swift`、测试。
- **验收：**单条超大、降级后仍超大、极小的注入预算三种情形下，每次 `insert` 结束都满足上限。
- **分工：**chore-worker。

#### F9 导入在入口处设读取上限（R09）

- `read` 在读取前检查大小：超过硬上限（初值 8 MB，为仅名字阈值的 4 倍）直接放弃该模块并计数。
- 目录列举改为有界枚举：最多读 20000 项，之后排序取前 2000，并标记结果被截断。

  `Imports/ImportCompletion.swift`、测试。

- **分工：**implementer。

### 阶段三：让"通过"可信

#### F10 内存基准默认隔离、口径不混用（R11）

- 每一轮都使用脚本自建的临时诊断目录，不再依赖调用方设置环境变量。
- 采样同时返回数值和口径。回退到 RSS、场景被跳过、读数未稳定、文件未实际打开，
  都判为"不具备通过证据"，退出码 2，与失败（1）区分。
- 应用增加一个诊断钩子：窗口就绪后把实际打开的文件、窗口尺寸、窗口是否在屏幕上写到指定文件，
  脚本据此核对。脚本同时记录二进制路径与摘要、提交号、工作区是否干净、分配器模式，
  以及 `footprint` 中 IOSurface 和 CoreAnimation 两类的读数。
- 判定逻辑可以用假采样器驱动，另加一个不启动应用的自测脚本覆盖上述分支。
- **涉及文件：**`scripts/mem-benchmark.sh`、新增 `scripts/tests/mem-benchmark-selftest.sh`、
  `App/AppDelegate.swift`（诊断钩子）、`docs/DEVELOPMENT.md`。
- **验收：**自测脚本覆盖通过、失败、无证据三类结果；真实运行的输出包含全部记录项。
- **分工：**implementer。

  检查改为：正文区域内有文字像素、行号栏内有行号、窗口打开的确实是样本文件。

## 5. 本次核实的可重现输入

报告附录的探针原样可用（R01、R02、R06、R10、R03）。本次补充的实测如下，均在临时目录里运行：

- **正则耗时曲线与可中止性。**对 `SearchEngine.matches` 依次传入 18 到 26 个 `a` 加 `!`；
  另用 `enumerateMatches(options: [.reportProgress])`，在回调里超过 0.25 秒即置 `stop`。
- **格式化峰值。**把 `JSONFormatter.swift`、`XMLFormatter.swift` 与一个小入口编译成命令行程序，
  对 48000 个对象的紧凑 JSON（5.55 MB）和 60000 个 `<item>` 的 XML（4.95 MB）
  分别运行"仅载入"和"载入并格式化"，用 `/usr/bin/time -l` 读 peak memory footprint。
- **深嵌套。**同一程序对 `[` 重复 n 次加 `]` 重复 n 次、`<a>` 重复 n 次加 `</a>` 重复 n 次运行，
  n 取 1000、10000、30000、50000，记录输出大小和退出码（139 即 SIGSEGV）。只在隔离子进程里做，
  不要在应用里对真实文档试。
- **原子写入对文件身份的影响。**对一个权限 640、带自定义扩展属性的文件，
  和一个指向别的文件的符号链接，分别执行 `Data.write(to:options: .atomic)`，
  前后用 `ls -li` 与 `xattr -l` 对比。
