# Karu 本机实测与发布

本流程整理自工程台账和经用户确认迁移的 Claude 项目记忆：2026-07-31 起先安装本机实测，
只有用户明确说“发布”才正式发版；2026-08-10 补充替换安装前必须退出旧实例。
当前用户指令优先。签名、安装等已授权步骤不反复询问，但不绕过操作系统或 Codex 权限限制。

## 固定身份与职责

- 产品及产物：Karu、Karu.app、Karu.dmg、Karu.zip。
- bundle ID：`dev.enkin.TinyEditor`；公证钥匙串 profile：`tinyeditor-notary`。
  保留既有标识及 Sparkle 更新身份，不因旧产品名随意修改。
- 版本与 build 位于 `scripts/bundle-macos.sh`；依赖锁定在 `Package.resolved`。
- 打包/发布脚本修改、签名、公证、发布和替换安装由主会话执行，不委派。
- 私钥、`.p8`、`.env*`、`.secrets.env` 不入仓库、产物或日志。
  使用现有钥匙串凭据引用，不索取、导出或保存用户密码。

## 阶段一：修改后预装本机

仅应用代码变更需要此阶段；纯文档或 Codex 配置改动无需重装应用。

1. 按 [DEVELOPMENT.md](DEVELOPMENT.md) 验证，检查 diff 与未完成项。
2. `bash scripts/bundle-macos.sh` 生成 `build/Karu.app`；默认 Developer ID 签名。
   `SIGN_IDENTITY=-` 仅用于明确需要的本地 ad-hoc 检查，不把它当作可分发版本。
3. 正常请求已运行的 Karu 退出，确认用户未保存内容的处理完成，并核对旧实例确实退出。
   若保存确认阻止退出，交给用户处理；禁止用强杀跳过。
4. 在确认源 bundle 完整且旧实例已退出后，替换 `/Applications/Karu.app`。
   仅操作该已核实目标，优先保留可回退副本至新实例启动成功。
5. 启动安装位置的应用，核对进程实际路径及版本，报告“已装本机待实测”。

此阶段不升版本、不打标签、不运行 release-macos.sh，不上传发布资产。
同版本预装属于测试构建，不能依赖 Sparkle 自动更新来确认测试代码已装入。
运行中覆盖 bundle 曾导致旧实例与磁盘版本错位、Sparkle 更新报错；正式安装也必须先退出。

## 阶段二：用户明确要求发布

1. 确认本机实测结论、待发内容、工作区差异及发布授权。用户说“发布”后，正常发布链
   在该授权范围内连续执行，不在每一步重复确认。存在未解决验收问题时先说明具体问题。
2. 主会话更新版本号及递增 build。只提交本次已审查的文件，不夹带用户原有未提交改动；
   记录源码提交、版本和产物的对应关系，验证后不得悄悄换入未验收代码。
3. 完成全量 Swift 测试、视觉冒烟与内存基准；三种内存场景不得把 SKIPPED 当作通过。
   记录系统环境，预算判断遵循 [ARCHITECTURE.md](ARCHITECTURE.md)。
4. 发布前用临时副本做小签名检查，尽早发现证书/钥匙串问题；不得改签用户应用来探路。
5. `bash scripts/release-macos.sh`：release 构建、由内向外签名、公证、装订、
   重打 ZIP、Sparkle EdDSA 签名、生成 appcast.xml、制作 DMG、Gatekeeper 终验。
   私钥留在钥匙串。读取脚本当前输出，核实每一步完成，不能仅凭产物文件存在判断成功。
6. 检查 app 的版本/build、签名公证状态及产物密钥排除检查。核对 appcast 的版本、
   build、下载地址、长度与签名匹配本轮 ZIP。
7. 为对应源码提交建立 `vX.Y.Z` 标签并推送，用现有 GitHub 发布通道上传三个资产：
   `Karu.dmg`、`Karu.zip`、`appcast.xml`。脚本只生成产物，不负责上传。
   发布说明记录用户可见变化与已知限制；不要覆盖已有发布而不核实原因。
8. 从线上读取 `releases/latest/download/appcast.xml`，确认解析得到本轮版本/build，
   三个资产可访问且更新包与签名信息一致。上传成功不等于更新链已验证。
9. 按阶段一的“退出旧实例 → 替换 → 启动”步骤安装本轮正式版，消除测试构建与发布版错位。
10. 更新 [LEDGER.md](LEDGER.md)，记录验证、本机实测、版本/build、发布与更新源检查结果。

## 失败处理

- `codesign` 的 `errSecInternalComponent` 曾由登录钥匙串锁定导致，但并非唯一原因。
  先取证确认；确需解锁时让用户通过系统界面操作，不读取或记录密码。
- Sparkle `sign_update` 无输出挂起曾是钥匙串访问提示；先检查是否等待用户操作，
  不因历史上允许过访问就假定当前证书、工具路径与系统权限仍然有效。
- 构建、测试、签名、公证、更新签名或上传任一步失败，报告阶段和证据；修复后重跑必要部分，
  不跳过检查、不伪造通过、不自动撤销用户改动。
- 安装失败保留或恢复先前已核实的本机 bundle；不要将未验证产物标记为已安装。
- 权限被拦截时解释具体操作与原因，保留已完成的产物和日志，再按当前权限流程处理。
- `notarytool` 返回协议 HTTP 403 时，记录服务端原文并由账户持有人核对对应团队的
  Developer Program 协议；不读取或替换私钥来试错。签署后早期请求仍可能被拒绝，
  不反复重打包；用户要求再试时可提交同一已验签 ZIP，并核对源码与产物未变。
  公证 Accepted 后可由主会话继续原脚本的装订及后续阶段，记录请求 ID，避免重新签名
  后混用不同构建。本项目 v0.10.0 已验证这条恢复路径。
