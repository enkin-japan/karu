- **环境**：Apple M6（12 核，32 GB），macOS 27.2（26B123），Apple Swift 6.4.2（Swift 5 模式），2026-11-15。

## 8. 超出目标的项目、原因与建议（未改代码）

1. **索引常驻超 5 MB（真实 5,000 文件仓库 typeshed：+6.9–7.7 MB，峰值 +8.4–8.6 MB）**。原因：逐个文件扫描后小块分配器保留了已释放页
   （Malloc Small 脏页 +8 MB，在用量只 +0.55 MB）；文件越多越明显，合成树（文件小而均匀）只有 +0.4 MB。
   建议（降级顺序第 1 步的延续）：扫描用的 UTF-16 缓冲与 token 缓冲在整个建索引过程中复用、按最大文件扩容，避免每个文件重新分配；
   或者把扫描放进专用 malloc zone，建完一轮后整体销毁。改动集中在 `Workspace/` 的扫描入口，复测用本报告 5.3 的 A/B。
   **T17.15d-B 已处理（达标）**：
   - 机制（本机 macOS 27.2 的 xzone malloc，独立小程序验证）：任何大小的块释放后都留在 footprint 里（10 MB 一块释放 30 s 后仍 +9.6 MB），
     `malloc_zone_pressure_relief` 对默认与全部 zone 都返回 0；自建 zone 销毁只还回约三分之一；只有 `MallocSpaceEfficient=1`（环境变量）会把空闲页标成可回收。
     所以「专用 zone」与「建完调用压力释放」都无效，索引的常驻就是建索引期间各尺寸分配的高水位，同一尺寸反复分配会复用，不随文件数增长。
   - 定位（App 内逐段关闭，typeshed）：遍历 +0.5–0.9、写库 +0.5、声明扫描 +2.0–2.6、`IndexedSymbol.extract` +1.1、签名摘要 +2.2–2.8 MB；
     去掉 14 个 >64 KB 的文件后总增量 +2.8 MB。单文件进程内峰值：331 KB 的 `winerror.pyi` 带摘要 4.84 MB（摘要器单独 3.55 MB），
     即大文件的摘要器（15–25 倍文件大小）定下了高水位。扫描器与 UTF-16 / token 缓冲在 `Analysis/`（另一位 implementer 正在改，本阶段不动），
     扫描器已按 16 K 单元分步，token 缓冲不随文件变大。
   - 做法（只在 `Workspace/`，队列与线程模型、schema 2 不变）：`extract` 改为一遍流式（`forEachDeclaration(from:to:)`，不再物化声明数组和中间
     pending 数组，签名在参数到齐后回填，结果与原两遍算法逐项相同，有测试）；`IndexSignatures.enrich` 原地改写（`consume`，不再复制一份符号数组）；
     **超过 `IndexScope.richSignatureMaxBytes`（64 KB）的文件不做签名摘要**，保留声明里的参数名签名 `(a, b)`（方案 §11 降级「大模块只留名字」）。
     受影响：typeshed 5,452 个可索引文件中 14 个、CPython 标准库 1,042 个中 43 个，这些文件的符号在补全列表与工作区符号里显示参数名而不是带类型的摘要；
     名字、类别、位置不变（App 内两版都是 5,451 文件、187,592 个符号）。
   - 读数（App，同一组交替 3 轮，每轮新诊断目录，至少 10 s 后稳定取值，18:37–18:41，负载 3.1–5.1；增量对同轮同二进制的无索引启动）：

     CPython +3.1 / +3.1 / +4.2 → +2.7 / +2.7 / +3.5 MB（峰值 +4.1–4.4 → +3.5–3.8 MB）。

   1 MB JSON 等没有声明的文件不重画，读数不变）。HEAD 在第一次交互时付同样的成本（验收套件：打开后 +65 MB，手动唤起后 +73 MB），详见台账 T17.15d-A。
5. **10 MB 文件重扫后第一个成员键超 50 ms**（Go 71 ms、Swift 61 ms，n=8；关推断对照 52–55 ms），以及 T17.15a 的「每键前刚重扫」最大 58–66 ms：
   超出部分不是推断（推断 1.4–6.8 ms），而是按键上现建查询索引（7–12 ms）加检查点。正常键入（真实窗口）p95 ≤15 ms。属 T17.15a 已知的最坏情形，可不处理。
6. **编辑后第一键的词法状态推进单次 45–57 ms**（large.py、多样名字、混合 Markdown；5 MB 单行 JSON 178 ms）——T17.15a 记过的「上下文检查点一次重扫」。建议同样分片。
   **T17.15d-A 已处理**：真实窗口里这一次是补全的上下文检查点只在请求时建立（跳到末尾后第一次请求从 0 扫起）；单行 JSON 则因 `didProcessEditing`
   报整段，行尾每次键入都让整行检查点失效。现在：检查点按 `willProcessEditing` 的精确范围失效；长行里编辑点前 32 K 以外的行内检查点保留；
   编辑点之后的检查点作为「待确认」平移，推进到时状态相同即整批恢复；语言切换、编辑停顿和模块开关之后，两套检查点由分片任务推进到文末，最长一片 ≤4.0 ms
   （单行 JSON 159 片共 383 ms）。键入阶段词法推进最长一次 large.py 47.5–64.1 → **0.0–0.1 ms**、多样名字 50.5–104.4 → **0.1–0.2 ms**、
   混合 Markdown 34.7–35.5 → **0.6–0.9 ms**、单行 JSON 200–205 → **2.4–3.9 ms**；顺带首次跳到末尾的推进 54–193 → 0.0–3.4 ms
   （第 6.2 节「10 MB 首次跳到末尾」那一趟着色降到 2–14 ms）。
7. **浅色主题两个类别的色值**：JSON 键应为 `#0451a5`、CSS 属性名应为 `#e50000`（Light Modern），Karu 沿用变量色。只是浅色色板两处映射，
   改后浅色一致率约可从 94.2% 升到 95% 以上（JSON 约 330 个单元、CSS 约 230 个单元）。深色不受影响。
   **T17.15d-B 已处理**：新增两个类别 `TokenKind.jsonKey`（JSON / JSONL 的键，Light Modern `#0451a5`）与 `.cssProperty`（CSS 属性名，`#e50000`），
   深色都仍是 `#9cdcfe`；`LanguageDefinition` 加 `propertyStringKind`，只有 JSON / JSONL 传 `.jsonKey`，CSS 的属性名规则改用 `.cssProperty`。
   Markdown 列表标记、TOML 键、YAML 带引号的键仍是 `.property`（颜色不变，有测试）。同一套导出与比对（第 9 节）：浅色 94.2% → **95.4%**
   （一致单元 41,474 → 42,018，不一致 2,559 → 2,015；`json.json` 61.7% → 100%、`jsonl.jsonl` 69.9% → 100%、`css.css` 54.3% → 72.2%，
   嵌入的 `fences.md` 78.4% → 80.6%、`page.html` 71.1% → 73.3%）；深色 97.3% → 97.3%，逐样本不变（不一致单元仍 1,177）。
   CSS 余下的浅色差距是自定义属性 `--x`（Light Modern 的 `source.css variable` 也用 `#e50000`，Karu 着变量色）与属性值关键字（见第 4 节），未改。
8. **1 MB JSON 远跳时一趟着色 p95 38.5 ms、最大 47 ms**（约 4,860 个单元一趟），而 Python 同样大小约 6–8 ms；附近小步重绘未单独测 JSON。
   建议用 `KARU_T177_PHASES` 同样的分相计时看 JSON 档案的耗时在哪一步。
9. **压力夹具超 99 MB**：10 MB 多样名字（113 MB，M17 状态约 26 MB）、两个 10 MB 窗口（146 MB）、5 MB 单行 JSON（258 MB，TextKit 排版）。
   都低于 v0.12.0 同条件的读数。前两项若要压到 99 MB 以下，按 §11 降级顺序第 3、4 步：大文件只保留模块级摘要、远处普通词不入词索引，代价是这类文件的召回率；
   需要 main 决定是否在 M17 内做。
   **用户决定（2026-11-15）：判通过，不做降级**。99 MB 上限只约束三个正式场景；这几项只在开发文档记录，README 与更新推送不写。
10. **测量口径**：`mem-benchmark.sh` 的稳定采样在 v0.12.0 的 10 MB 场景上会取到台阶之前（见 5.1）；`/Applications` 的基线读用户自己的窗口尺寸与字号。
    建议脚本加一个最短观察时间（如 `KARU_BENCH_MIN_WAIT_SECONDS`，默认 0 保持兼容），并在报告里注明基线的偏好域；
    或在 DEVELOPMENT.md 规定基线对照同时看长窗口读数（本报告的做法）。
    **T17.15d-B 已处理**：`mem-benchmark.sh` 新增 `KARU_BENCH_MIN_WAIT_SECONDS`（默认 0，行为与旧版相同）。启动后这段时间内的读数不参与稳定判定，
    稳定区间必须整个落在它之后；最长等待不足「最短观察时间 + 稳定窗口」时自动延长。脚本头与 DEVELOPMENT.md 已写明。
    实测（候选二进制，诊断目录隔离）：默认时三个正式场景稳定于 0.2 / 0.8 / 1.0 s（31.8 / 51.2 / 87.3 MB），设 6 s 时都稳定于 6.1–6.2 s
    （31.4 / 51.2 / 87.5 MB）。没有对 `/Applications` 的 v0.12.0 复测：它使用用户自己的偏好域，窗口尺寸可能被写回。
